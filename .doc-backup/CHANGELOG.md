## [P11-补7] 2026-10-15 — 自动刷新真正接通 + 一个静默改写用户输入的缺陷

用户要求：「自动刷新真正接通」。此前它只是**一个被记住的设置**，不会定时拉取。

### 实现：定时与"刷什么"解耦

```
AutoRefreshEffect（挂在根壳，全应用一处）
  └─ 到点 → AutoRefreshState.tick++（Compose 可观察）
              └─ 各页面的 Holder 观察到 tick 变化 → 重新拉自己的数据
```

新增工具时**不需要碰定时逻辑**，只要在它的 Holder 里观察 tick 即可。

| 关键决定 | 理由 |
|---|---|
| **只在应用前台计时**（`repeatOnLifecycle(STARTED)`） | 兑现数据设置页上那句「不会在后台常驻请求」。后台存活要申请前台服务/精确闹钟权限，工具类应用没有理由要 |
| 回到前台**重新计时**，不补算漏掉的次数 | 补算会在回到前台瞬间**连发多次请求**，正是要避免的 |
| 关闭时 `nextDelayMillis` 返回 **null** | 返回 0 会疯狂循环；返回极大值会留下永不醒的协程。null 让调用方显式地不启动 |
| 间隔非法（0/负数/超 24 小时）一律拒绝启动 | 防止旧数据或被手改的 prefs 导致**无限请求**（数据源是积分制的） |
| 开启时**不额外补刷一次** | 各页面进入时本来就会加载，再补一次是重复请求 |
| 加 `inFlight` 防重入 | 用户点「刷新」的瞬间正好到点，两次请求会同时飞出去 |

`tick` 必须是 **Compose 可观察状态** —— 本项目已经因为"把状态藏在普通属性后面"
踩过两次（P09 工具启停、P11 返回键），这次没重复犯。

### ★★ 端到端验证抓到一个静默改写用户输入的缺陷

**第一次验证结果：自动刷新没触发**（请求数 190 秒内一直是 2）。

加日志后发现**定时器本身是好的**（`delay=300000, lifecycle=RESUMED`），
但读到的间隔是 **5 分钟**，而 prefs 里明明存的是 **2 分钟**。

**根因**（`SettingsStore.load()`）：

```kotlin
autoRefreshMinutes = prefs.getInt(KEY_AUTO_REFRESH_MIN, 30).coerceIn(5, 24 * 60)
//                                                                  ↑ 最小值写死 5
```

而新的数据设置页允许输入 **1–1440**。两边范围不一致 →

> 用户填「2 分钟」→ 落盘确实是 2 → **读回来被静默改成 5** →
> 界面仍显示「2 分钟」，实际按 5 分钟跑，**全程没有任何提示**。

**修复**：读取范围改为引用 `AutoRefreshPolicy.MIN_MINUTES / MAX_MINUTES`，
**与 UI 共用同一个来源**，不会再漂移。并加了一条断言把两个范围钉在一起。

> ★ 这类缺陷的可怕之处：保存成功、界面正确、没有报错，
> **只有行为与显示不符**。单测全绿、界面看着正常，都发现不了 ——
> **只有端到端数请求次数才抓得到。**

### 实测证据

| 验证 | 结果 |
|---|---|
| 定时器启动 | ✅ `minutes=2 delay=120000 lifecycle=RESUMED` |
| 修复前后对比 | ✅ 修复前读到 5 分钟（被改写）；修复后 2 分钟 |
| **到点真的刷新** | ✅ `T+0 请求数=2` → `T+150s 请求数=3` |
| tick 日志 | ✅ `到点触发 tick=1` |
| 请求时间戳间隔 | ✅ `07:42:57 → 07:44:35`（≈ 2 分钟计时） |

### 单元测试

**197 个用例 / 0 失败**，新增 11 个 `AutoRefreshPolicyTest`，
其中包含用**虚拟时钟**验证"到点真的会触发""差 1 毫秒不触发""取消后不再触发"。

### 顺带修正

  它会显示在「关于」页，停在旧值会误导排查方向。

## [P11-补6] 2026-10-15 — 游戏标签左右滑动切换 + 一个死循环缺陷

用户要求：「主界面的应该是可以左右相互滑动的来切换的三角洲和鸣潮之间的界面」。

### 实现

用 `HorizontalPager`（属于 `compose.foundation`，**没有引入新依赖**）
把两个游戏标签合成一个分页容器 `GamePagerHost`。

自己写手势也能做，但分页滑动有几个不容易做对的细节，官方 pager 已经处理好了：
**速度阈值与惯性**、**边缘回弹阻尼**、**与纵向列表滚动的手势冲突**。

三个关键设计决定：

| 决定 | 理由 |
|---|---|
| **只有游戏标签可滑**，二级页面不可滑 | 二级页做横向手势会和返回手势、横向筛选条**冲突** |
| 滑动**不触发导航转场** | 位置已由 pager 跟手渲染，再放一次转场会**滑两次**。为此新增 `UbNavigator.syncTab()`（只同步状态、不产生转场） |
| 点标签与滑动**双向同步** | 缺任何一边都会出现"点了标签页面没动"或"滑过去了底部还亮着上一个" |

### ★★ 实现过程中撞到一个死循环缺陷

**现象**：滑动切到鸣潮后，底部高亮**仍停在三角洲**；点三角洲标签也像没反应。

**排查**：加日志把同步链路打出来，日志是决定性的：

```
settledPage=1 → nav.current=game/wuwa      ← 同步成功 ✅
然后：settled=0, nav.current=game/delta      ← pager 被重建，状态回到第 0 页 ❌
```

**根因**：`UbNavHost` 的 `AnimatedContent` 用 `targetState = navigator.current`。于是：

1. 滑动 → pager 到第 1 页
2. 同步 `nav.current = game/wuwa`
3. `AnimatedContent` 认为"路由变了" → **重建内容**
4. `rememberPagerState` 是内容里的状态 → **pager 被重置回第 0 页**
5. 第 4 步又同步 `nav.current = game/delta` → **回到步骤 1**

**修复**：把两个游戏标签在**转场层面折叠成同一个状态** `GAME_PAGER`：

- 三角洲 ⇄ 鸣潮：targetState 不变 → pager **不被重建**，状态得以保留
- 进入二级页 / 切到「我的」：targetState 变化 → 正常播放转场

> ★ 用常量折叠而不是"让两个路由相等"：前者只影响转场，
> **导航语义完全不变** —— 底部高亮、返回栈仍能正确区分两个标签。

### 单元测试

**186 个用例 / 0 失败**。

| 测试类 | 用例 | 针对 |
|---|---|---|
| `UbNavigatorTest` | 7 → **19** | 方向 8 个 + `syncTab` 4 个 |
| `GamePagerHostTest` | **5**（新） | "哪些路由进分页容器"的判定 |

`isGameTabRoute` 单独测试的理由：它是分页容器准入的**唯一依据**，
判定过宽会把二级页塞进 pager（手势冲突），过窄则滑动失效 ——
两种错误都**不会崩溃**，只能在真机上"感觉怪"，正是最该被钉住的那类。

### 模拟器实测证据

| 验证项 | 结果 |
|---|---|
| 左滑 → 鸣潮 | ✅ |
| 右滑 → 三角洲 | ✅ |
| 底部高亮跟随滑动 | ✅（修复后） |
| **点**标签双向切换 | ✅ |
| 边界（已在三角洲再右滑） | ✅ 停住不动 |
| 二级页内左滑 | ✅ 不切换（今日密码页不受影响） |
| 二级页返回 | ✅ 正常逐级返回，应用不退出 |

> **教训：两个"各自都对"的机制叠在一起会互相打架。**
> pager 同步导航状态是对的，`AnimatedContent` 按路由重建内容也是对的，
> 但合在一起就形成"同步 → 重建 → 状态回退 → 再同步"的闭环。
> **这类缺陷靠读单个模块的代码看不出来，只有把链路日志打出来才看得见。**

## [P11-补5] 2026-10-15 — 页面转场方向（用户反馈「转场杂乱无章」）

### ★★ 缺陷：转场完全不区分方向

**用户原话**：「返回某一级菜单应该是从左边往右淡出，进入则是反过来，而不是杂乱无章的」。

**根因**：`UbNavHost` 的 `transitionSpec` 里，**前进和返回共用同一个动画**：

```kotlin
// 修改前 —— 无论前进还是返回都是这一套
(slideInHorizontally { it / 6 } + fadeIn()) togetherWith
    (slideOutHorizontally { -it / 8 } + fadeOut())
```

注释里写着「前进：新页从右滑入；返回：新页从左滑入（由调用方决定的简化处理）」，
但**那个"简化处理"从来没有实现** ——
于是**按返回键时，页面仍然从右边进来**，与用户的动作预期完全相反。

> 这是"注释描述了一个不存在的实现"的典型案例：
> 注释读起来像是已经处理了，实际代码里没有任何分支。

### 修复：方向由**导航动作**决定，而不是由页面自己猜

1. 新增 `NavDirection` 枚举（`Forward` / `Backward`）
2. `UbNavigator` 记录 `lastDirection`：
   - `navigate()` → `Forward`
   - `back()` → `Backward`
   - `switchTab()` → `Forward`（标签之间没有层级关系，用侧滑会制造"层级"的错觉）
3. `UbNavHost` 按方向选择转场：

| 动作 | 新页 | 旧页 |
|---|---|---|
| **进入** | 从**右**滑入 | 往**左**退出（位移 1/3 + 淡出） |
| **返回** | 从**左**滑入 | 往**右**退出（完整位移 + 淡出） |

> 用**枚举**而不是布尔值：将来若加"横向切换标签"这类第三种方向，
> 布尔值就表达不了，届时全项目都要跟着改。

### 单元测试

**177 个用例 / 0 失败**。`UbNavigatorTest` 从 7 → **15** 个用例，
新增 8 个专门钉住方向，其中最关键的两条：

- `back 记为返回` —— 若回归，页面会再次从右边进来

## [P11-补2] 2026-10-15 — 按用户反馈修复（弹药无价格 / 图片 / 筛选 / 首页来源行）

用户反馈五条，逐条处理。**其中一条查出是我的解析写错了字段路径。**

### ★★ 缺陷 1：弹药物价全部显示「暂无成交数据」

**用户原话**：「你的弹药物价没有显示数据呀，没有价格啥的」。

**排查过程**（这次特意先拿实测响应再动手，因为字段路径此前已错过三次）：

给 HTTP 层加了一条成功响应的**结构摘要日志**（只记路径与前 2000 字符，
**不含请求头所以不含 API Key**），拿到真实响应：

```json
{"ammoDetail":{"armorHarmLevel":"高","penetrationLevel":6},
 "avgPrice":4229,                                                  // ★ 价格在顶层
 "hasValidPriceData":true,
 "priceStats":{"avgPrice":0,"dataPoints":0,"latestPrice":0,...}}   // ← 全是 0
```

**根因**：我原先读的是 `priceStats.latestPrice`，而该接口的价格在**顶层 `avgPrice`**。
两者**同时为 0 时看不出差别**，所以一直没暴露。

**修复**：价格改读顶层 `avgPrice`，`priceStats` 保留为兜底。

**修复后实测**：`弹药 113 条｜有价格 104 条｜击穿等级 [1,2,3,4,5,6,7]`

> **教训：字段路径必须照抄实测响应，不能从"看起来更专业的嵌套结构"推断。**
> 已把字段路径**钉进单元测试**（照抄真实响应），这类错误不会再犯第二次。

### ★★ 缺陷 2：涨跌幅显示「↑ 0.0%」——这是在编造数据

**根因**：接口在无成交时返回 `priceChangePercent: 0`，
但那**不是"价格没变"**，而是"根本没有可用于比较的样本"。
直接显示成「↑ 0.0%」等于替数据源编了一个"持平"的结论。

**修复**：新增 `dataPoints`（样本数）字段，**样本 ≤ 0 时涨跌幅一律为 null**。

**并且**：全部 113 条的 `dataPoints` 都是 0 —— 该数据源**只有均价、没有历史样本**，
所以涨跌幅在这份数据上本来就无法计算。UI 如实说明：
「该数据源没有历史样本，暂不显示涨跌」。

> ★ 这里我先写错了提示文字，写成「价格暂时无法获取」，
> **与同一屏上显示的真实价格自相矛盾**。截图一看就发现了。
> **教训：提示文字必须与屏幕上的实际内容一致，写错比不写更糟。**

### 缺陷 3：没有图片

**用户原话**：「这子弹单纯只有名称，没有图片呀」。

**实测发现**：两个接口**都返回 `pic` 与 `prePic`**，且指向
**腾讯官方图床 `playerhub.df.qq.com`**（不是第三方站自己的服务器）。

**修复**：新增 `core/design/UbImageLoader.kt`（零新增依赖）：
- `HttpURLConnection` + `BitmapFactory` 自写加载
- **`LruCache` 按字节数限制**（取可用堆 1/8）—— 按条目数限制会让内存占用失控
- **`inSampleSize` 采样解码** —— 接口给的是原图，我们只显示 48dp
- **同一 URL 去重**（`inFlight` map）—— 快速滚动时不会并发重复下载
- 失败显示占位底色而不是留白（留白会被误认为"这个物品没有图"）

### 缺陷 4：弹药缺少搜索 / 分类 / 等级

**用户原话**：「应该加入搜索筛选分类啥的功能，以及子弹应该显示当前的等级
（是一级，还是二级啥的）」。

**修复**（`AmmoPriceScreen` 重做）：
- 搜索框（按名称或口径）
- **口径分组筛选** + **击穿等级筛选**，选项**从真实数据归纳**，不写死
- 显示 `ammoDetail.penetrationLevel`（**这才是玩家说的"一级弹/二级弹"**）

> ★ 澄清一个概念混淆点：`grade` 是**稀有度**（★1–★6），
> `penetrationLevel` 才是**击穿等级**。两者都显示、分别标注，
> 否则用户会把 ★6 当成"6 级弹"。

**同时修了一处布局缺陷**：四个元信息标签挤在一行会让「护甲伤害 高」折行，

### 缺陷 5：物品物价搜索会搜到枪械皮肤

## [P11-补] 2026-10-14 — 真机反馈修的两个严重问题

> 用户装到真机（vivo V2307A / Android 16）后反馈两个问题。
> **这两个都是模拟器测不出来的** —— 一个被我的验证方式掩盖，一个纯粹是设计缺失。

### ★★ 问题 1：二级页面按返回**直接退出应用**

**用户原话**：「我在里面进入了一个二级菜单，手机直接返回，想回到一级界面，
结果直接退出软件了」。

**根因**（严重，属状态可观察性缺陷）：

```kotlin
// UbNavigator —— 错误写法
private val backStack = mutableListOf(initialRoute)   // ← 普通 List，不是 Compose 状态
val canGoBack: Boolean get() = backStack.size > 1
```

`BackHandler(enabled = navigator.canGoBack)` 在组合期读它时，
**Compose 不会把这个读操作记为依赖** —— 于是 `enabled` 停在某个过期值上，
返回键没有被拦截，事件交给系统 → **Activity 被结束**。

**这与 P09 修工具启停时的 `isToolDisabled()` 是同一类 bug**：
**把状态藏在普通 getter 后面，重组就会静默失效。** 同一个坑踩了两次。

**修复**：`UbNavigator` 增加可观察的 `stackDepth`，
`canGoBack` / `isRootTab` 都读它建立依赖；所有改栈的方法同步更新它。
**新增 7 个 `UbNavigatorTest` 用例**把栈深与判定值的同步钉死。

### ★ 问题 2：首页按一次返回就退出（缺少"再按一次"缓冲）

**修复**：`BackHandler` 改为**常开**，自己决定三种行为：

| 情形 | 行为 |
|---|---|
| 有历史 | 正常后退 |
| 已在根标签，第一次按 | 显示「再按一次返回键退出」提示，**不退出** |
| 2 秒内再按 | 退出 |

**实现**：`core/design/UbExitHint.kt`
- `ExitConfirmState` —— 双击退出状态机（时钟可注入，便于精确测边界）
- `UbExitHint` —— 自己画的提示条，**不用平台 Toast**：
  Toast 在 vivo / MIUI / ColorOS 上样式各异且不受控，与设计系统不统一
- 标了 `liveRegion = Polite`，屏幕阅读器会朗读（无障碍要求）

### ★★★ 单元测试抓出了我自己写的溢出 bug

`ExitConfirmState` 最初把「没按过」写成哨兵值：

```kotlin
private var lastBackAt: Long = Long.MIN_VALUE
...
if (now - lastBackAt <= windowMillis)   // 1000000 - Long.MIN_VALUE → 溢出成负数
```

`now - Long.MIN_VALUE` **整数溢出变负**，负数恒 `<= window` ——
于是"第一次返回"被判成"窗口内第二次"，**按一次就直接退出**，
**恰好是这个功能本该避免的行为**。

8 个用例里有 4 个当场失败。改用 `Long?` 表达"还没有值"后全部通过。

> **教训：用哨兵值做减法比较必然踩溢出。**
> 表达"还没有值"就该用 `null`，不要用 `Long.MIN_VALUE` 这类极端值。
> **这是纯逻辑 bug，只有单元测试能抓住** —— 真机上表现为"按一次就退出"，
> 与"功能没做"无法区分，光靠手测根本定位不到。

### ★ 模拟器测不出来的原因（对验证方式的反思）

问题 1 之所以一直没被发现，是因为我在模拟器上**用 `adb shell input keyevent BACK` 测过**，
但每次的路径都没走到"二级页面 + 系统返回"这个组合上，
而且返回键由系统处理导致的 Activity 结束**不会留下崩溃日志** ——
我此前一直是靠"logcat 无 FATAL"来判断没问题，**这个判据对返回键失效**。

| 判据 | 能发现 | 不能发现 |
|---|---|---|
| logcat 无 FATAL | 崩溃、异常 | **返回键/手势等交互错误**（进程被正常结束，没有日志） |
| 文本 dump | 元素是否在 | 交互是否流畅、视觉是否正确 |
| 像素采样 | 视觉正确性 | 交互时序 |
| **真人手指操作** | **交互问题** | 难以规模化 |

**结论：交互类缺陷必须真人操作。** 后续 UI 测试（P10）要用
`androidx.compose.ui.test` 的 `performClick` + `Espresso.pressBack` 覆盖这条路径。

### 真机验证结果

用户确认：**「目前整机测试下来，正常」**。

### ★★ 一次判断方向的错误（用户裁决纠正）

我先选了 `Regular`，**理由是"对比度衰减更大 = 模糊更强"**。

**它不是"模糊更弱"，而是"更通透"**，我用一个错误的单一指标（衰减越大越好）做了决策。

> **教训**：用**单一量化指标**代替审美判断是危险的。
> 指标能证伪（"完全没模糊"），但不能定优劣（"哪种更好看"）。
> **该让用户看对比图定的事，不要自己用一个数字替他决定。**

## [P09-补] 2026-10-14 — 深色模式下 tab 栏发灰白（用户报告）

> 用户原话：「目前有 bug，就是在深色模式下，你这个 tab 栏为什么会显示为灰白色」。

### 量化确认（不是观感问题）

| 场景 | 底部栏像素 | 页面背景 | 判定 |
|---|---|---|---|
| 深色 · 首页 | `#0E0F12` | `#0E0F12` | 玻璃完全不可见 |
| **深色 · 设置页** | **`#999A9D`** | `#1A1C20` | **亮灰色块 —— 真缺陷** |

### 根因：Haze 的 regular 材质**只按浅色校准**

官方说明其光色 **「calibrated against native iOS 27 light appearance」** ——
**没有深色变体**。深色主题下它会采样页面里的浅色卡片，输出一块亮灰。

> **「库没有对应能力」不等于「问题不存在」** —— 用户看得见，就得修。

### 修法

原生 iOS/Android 材质都随主题切换，故补一层**与主题同向的材质色调**（画在玻璃之上）：

| 主题 | 色调 | 不透明度 |
|---|---|---|
| 浅色 | 白 `#FFFFFF` | 0.28 |
| 深色 | 近黑 `#0A0B0D` | 0.80 |

改在 `UbGlassSurface`（所有玻璃的唯一入口），**调用方零改动**。

### 同时修掉的相关项

1. **底部栏溢出屏幕**：`Modifier.fillMaxWidth()` 写在 `padding` **之前** →
   先占满全宽再内缩，胶囊必然超宽。已调序。
2. **玻璃内容未裁切**：Haze 只裁玻璃层，不裁子内容 → 补 `.clip(rounded)`。
3. **主题默认值改为「跟随系统」**（原写死「浅色」）：
   系统处于深色的用户第一次打开会看到亮色界面，第一反应是"这应用坏了"。

### 验证（A/B，切换系统主题）

| 系统主题 | 底部栏 | 页面背景 | 判定 |
|---|---|---|---|
| 深色 | `#0B0C0E` | `#0E0F12` | ✅ 融合 |
| 浅色 | `#F7F8F9` | `#F4F5F7` | ✅ 明亮，未被误压暗 |

**124 个单元用例 0 失败**（默认主题断言已同步更新）。

### 教训

1. **「用了现成库」不等于「各主题下都对」** —— 库的能力边界就是你的缺陷边界
2. **深色缺陷在浅色环境下测不出来** —— 我漏掉了「系统深色 + 跟随系统」这条最常见路径
3. **默认值要选不易出错的那个**
4. **量化胜于观感** —— 像素采样把"看着有点怪"变成硬证据

> **附带一次失败的自查**：排查时我用 `IndexOf("实验性")` 定位节点，
> 子串命中了「2 个可用 · 1 个实验性 · 1 个开发中」，导致正则截取偏移、
> 凭空造出一个假节点，白追了半天。
> **教训**：在结构化数据里用文本定位，必须用**带边界的完整属性匹配**，
> 否则工具会**制造**出你要找的 bug。

### ★ 为什么详情页需要独立状态机

详情页是**两个独立请求**的组合（当前价 + 历史），二者可一成功一失败。
`UiState` 只能表达整体成败，会丢失"价格取到了但历史失败了"这一信息 ——
而那对用户是**不同**的处境：应照常显示价格，只在图表位置说明历史取不到。

另设 **`NoPriceData` 为独立状态而非错误态**：
红线要求「无成交数据 ⇒ 显示『暂无成交数据』」。
混进错误态会让用户以为是故障，而实际只是"该物品近期没有成交"。

### ★★ 实测发现并修复的 4 个真实缺陷

| # | 缺陷 | 根因 | 处置 |
|---|---|---|---|
| 1 | **三个请求参数名全写错**（端点全部 400） | 凭直觉写 `keyword`/`objectIDs`/`objectID`；正确是 **`objectName`/`id`/`id`** —— 我**从响应体字段名反推**了请求参数名 | 按 P01 实测记录改正；加测试把三个名字一起钉住 |
| 2 | **HTTP 层丢掉了 4xx 的响应体** | 非 2xx 时直接 `Server(code)` 返回，**从未解析 body**，真正原因不可见 | 改为 **4xx 把 body 交上层解析**；5xx 仍归服务端故障 |
| 3 | **「没有数据」被显示成「服务故障」** | 服务端对无价格物品返回 `400 {"code":400,"message":"AMS 响应缺少 dataMap"}` —— 这是**数据缺失**，界面却说"临时故障，稍后重试"，**重试永远不会成功** | 新增 `AppError.noPriceDataSignal()` 归为 `NoPriceData`。**并加反向测试**：真正的 5xx/限流不得被吞成"无数据" |
| 4 | 空历史数组被包装成 `PriceHistory(points=[])` | 图表会画**空图表**而非给出解释 | 归一成 `null` |

> **缺陷 1 的教训**：本项目在 P01 **已经实测并记录**了正确参数名，
> 我却在写代码时凭印象写错、没有回看自己的实测记录。
> **教训是「有实测记录就要照抄，不要凭直觉」**。
>
> **缺陷 3 的教训**：错误分类必须匹配**用户能采取的行动**。
> "没有数据"要用户接受现实；"服务故障"要用户重试。混为一谈会让人做无用功。
> 这与 P06 的 `ApiKeyMissing` / `Unauthorized` 拆分是**同一类问题**。

## [P04-补2] 2026-10-14 — 玻璃实现切换为 Haze 2.0.1（用户裁决）

> 用户看过并排对比截图后裁决：**「显然那两种好，自己写的不好，按照那两种的来」**。

### ★ 基线变更（用户已批准）

| 项 | 原值 | 新值 |
|---|---|---|
| `composeBom` | 2026.02.01（ui **1.10.4**） | **2026.09.00（ui 1.12.1）** |
| 新增依赖 | — | `haze` / `haze-glass` / `haze-glass-material3` **2.0.1**（Apache-2.0） |
| `material3` | 1.4.0 | 1.4.0（不变） |

**为什么 BOM 必须一起升**：`haze-glass:2.0.1` 要求 `androidx.compose.ui 1.12.1`。
实测「保 BOM 1.10.4 + 用它」**做不到**：加 `strictly("1.10.4")` 后 `BUILD FAILED`
（`multiple version constraints with conflicting requirements`）。

**因此选择「把 BOM 换到与该库匹配的版本」，而不是放任版本被顶高** ——
`2026.09.00` 精确钉住 `ui/foundation/runtime/animation-core = 1.12.1`、`material3 = 1.4.0`。
实测确认是 **BOM 满足库**，不是库顶高版本。

### 为什么换（实测对比）

并排同形状、同尺寸、同彩色底面的对比（`screenshots/haze-vs-handmade.png`）：
自研实现只有**整体均质模糊**、胶囊边缘**溢出底色**、**无边缘光学**；
Haze `GlassStyle.regular` **精确裁切**且有**折射/收缩**。

Haze 另有自研没有的能力：菲涅尔边缘提亮、色散、光源位置、材质随尺寸自适应、
无障碍挂钩（`reduceTransparency`/`increaseContrast`/`showBorders`）、
以及**自动降级**（简化渲染器自动省略折射但保留色调与形状）。

> 官方明确声明「**do not promise pixel parity with another system**」。

### 修改与设计要点

`core/design/UbGlass.kt` 内部换成 Haze，新增 `ProvideHazeState` / `UbGlassSource`。
**`UbGlassSurface` 签名保持兼容 —— 调用方零改动。**
**所有玻璃仍只经 `UbGlassSurface`**，Haze 被隔离在这一个文件内，将来升级只改这里。

### 实测踩坑（已写入代码注释）

1. `shape` 属于 `GlassStyle`，**不是** `hazeGlass` 的参数
2. `HazeInput.Backdrop(state)` 需要 state 参数，不能空参
3. Haze 只接受 `RoundedCornerShape`，而设计系统用通用 `Shape` → 加转换函数
4. 内容必须标 `hazeSource`，否则玻璃后面什么都没有
5. Haze 首帧渲染比自研模糊慢 → 验证脚本等待需加长

### 切换后连带修掉的两处

1. **底部渐隐层变多余** —— 它是自研时代的替代方案；Haze 本身就会折射模糊其下内容，
   两层叠加让栏下文字发脏。删除后内容完整清晰。
2. **状态文案不一致** —— 设置页与数据源页仍写「1 个不可用」「无可用数据源，暂不可启用」，
   而该功能已改为「开发中 · 数据源待接入」。已统一。

| `game/deltaforce/DeltaForceRoutes.kt` | **工具路由下移到模块层** |
| `game/deltaforce/pricerange/` | 验收用的新工具（页面 + provider） |
| `feature/common/UbToolPage.kt` → `UbToolHost` | 由 provider 渲染完整页面 |

### ★ 实测发现的关键设计点：路由不能放公共层

首次尝试时路由常量仍写在 `core/navigation/UbRoutes.kt`，
意味着每加一个工具都要改**共享文件**——"不改公共代码"当场不成立。

**修正约定**：应用级路由留公共层；**工具路由归游戏模块所有**。

### 验收方法与结果

**方法**：新增工具前先对 10 个公共层文件取 SHA256，新增后再比对。

**结果：10 / 10 未改动。** 实际改动量：2 个新文件 + 2 处各 1 行。

**设备验证**：首页自动出现「价格区间 / 实验性 · 模拟数据」；
点击可打开；区间统计正确排除无成交物品；**零崩溃**。

### 另有：`verifyIntegrity()` 写了却没有任何调用点（由测试发现）

KDoc 写明"在应用启动时调用一次"，但全仓 grep 显示**只有定义处与测试引用它** ——
真机上启动自检从不执行。后果：注册表配错时不会立刻暴露。
**处置**：移到 `UbApplication.onCreate`。

> **教训**：**"写了自检"和"自检真的会跑"是两件事。**

### ★ 关键决策

| # | 决策 | 理由 |
|---|---|---|
| D19 | HTTP 抽象成 `HttpClient` 接口 | 业务不依赖具体实现；单测可注入假实现 |
| D20 | **不用 Kotlin `Result<T>`**，自定义 `EnvelopeResult` | `Result` 要求失败携带 `Throwable`，而 `AppError` 是密封类型 |
| D21 | **自写极小 JSON 解析器** | 见下方"关键发现" |
| D22 | `DataResult` 增加 `Unavailable` 第三态 | 让"数据源无法提供该能力"进入类型系统 |
| D23 | 缓存信封强制带 `schemaVersion` | 结构变更时**安全丢弃**旧缓存，不做兼容猜测 |

### ★★ 关键发现：`org.json` 在单元测试里是空壳 stub

首次运行单元测试：**29 / 40 失败**。根因**不是业务代码**：

> `org.json` 属 Android 框架，在 JVM 单元测试中只有**方法签名**，
> 一调用就抛 `RuntimeException: Method ... not mocked`。
> 因此所有涉及 JSON 的逻辑（解析正确性、错误映射、"0 不是价格"等**红线**）
> 都无法在无设备环境下验证。

**两条路，选择了后者**：给测试加第三方 `org.json` 依赖会造成
"测过的实现与运行时用的实现是两套代码"，测试结论不可迁移；
**自写实现**则零生产依赖、测试与运行时同一份代码。

自写实现额外提供语义化读取：`positiveLong()` 把 **0 / 负数 / 缺失一律视为「无数据」**，
把红线编码进 API 形状。

### 🟢 实测结论：两条路线都已跑通核心栈

| 能力 | Kotlin 2.2.10 | Kotlin 2.4.21（**已选定**） |
|---|---|---|
| Compose + 自研导航 | ✅ 11.76 MB | ✅ 11.85 MB |
| 官方 `navigation-compose` | ✅ 11.65 MB | ✅ 11.72 MB |
| 零依赖平台 `Modifier.blur` | ✅ 11.76 MB | ✅ 11.85 MB |
| `liquid-glass 0.2.3`（含降级档） | ✅ 11.85 MB | ✅ 11.90 MB |
| `haze 1.7.3`（纯模糊） | ✅ 11.73 MB | ✅ 11.78 MB |
| **`haze 2.0.1` + `haze-glass`（折射）** | ❌ metadata 不兼容 | ✅ **12.14 MB** |

> **选定 Kotlin 2.4.21 的唯一收益**：解锁折射式液态玻璃。
> 其余能力两条路线**实测完全一致**，故本次升级**不引入回归风险**。

### ★ 关键实测发现

| 发现 | 说明 |
|---|---|
| **Kotlin metadata 天花板** | 编译器只能读「自身版本 +1 minor」的 metadata。2.2.10 上限 `mv ≤ 2.3.x`，读不了 `mv=[2,4,0]` 的库 |
| **`Modifier.blur` 在 API < 31 被静默忽略** | 不崩溃，但玻璃"没生效"且用户不知道原因 → 必须主动判定并降级 |
| **`liquid-glass 0.2.3` 平台自动档在软件渲染下 SIGSEGV** | `Fatal signal 11 ... tid (RenderThread)`；强制 `Fallback` 档可用 |
| **AGP 9.x 内置 Kotlin 支持** | **不得**再 apply `org.jetbrains.kotlin.android`；只需 `kotlin.plugin.compose` |
| **`sdkmanager.bat` 会被分号拆参数** | 需用 `android.exe --sdk=... sdk install 'platforms/android-37.0'` |
| **无 GUI 验证必须先清理上一个 App 的窗口** | 否则 dump 读到的是别的应用 |

**另一项重要结论**：**自研玻璃（`Modifier.blur` + 半透明覆盖）只能做整体均质模糊**，
实测在 API 31+ 且软件渲染下**可用且观感可接受** —— 故 P02 先自研，
把"是否引入折射玻璃"作为一项独立裁决延后（最终在 P04 决定改用 Haze）。
