### ISSUE-017 · Haze 的模糊半径无法通过公开 API 调整（已实测确认）

| 项 | 内容 |
|---|---|
| 发现于 | P10，用户反馈「tab 栏要多些高斯模糊」 |
| 严重度 | 低（模糊本身正常，只是强度不可调） |
| 现状 | **模糊确实在工作**（实测：栏内局部对比度 12.93 → 6.03，衰减 2.1×） |

**试过并失败的路径**

| 尝试 | 结果 |
|---|---|
| `GlassStyle.regular(rounded) { blurRadius = 30.dp }` | ❌ `Expression 'regular' of type 'GlassStyle' cannot be invoked as a function` |
| `GlassStyle.regular.then { shape(rounded); blurRadius = 40.dp }` | ❌ `'val' cannot be reassigned`（该作用域里 `blurRadius` 只读） |
| `GlassStyle.regularDark` / `regularLight` / `clearDark` / `clearLight` | ❌ `it is internal`（Haze 内部按明暗自动选材质，不对外暴露） |
| `GlassStyle.Clear` 材质 | ✅ 可用，但**模糊更弱**（栏内对比度 8.35 vs `Regular` 的 6.03）—— `Clear` 的设计意图就是保留更多背景 |

**结论**：Haze 2.0.1 把模糊半径交给内部的 `GlassOptics` 决定，公开 API 只暴露
材质选择（`regular` / `clear`）与形状。**要继续加强模糊只能等上游，或换库。**

**已做的**：材质采用 **`Clear`**（用户看过对比图后裁决 ——
`Clear` 更通透，能看见背景的明暗结构；`Regular` 更雾但显得"塑料"）。
色调降至浅色 0.10 / 深色 0.55。

> ★ 裁决过程值得记：我先按"对比度衰减更大 = 模糊更强"选了 `Regular`，
> **那是用单一数字替用户做了审美决定**。指标能证伪（"完全没模糊"），
> 但不能定优劣（"哪种更好看"）。**该让用户看对比图定的事，不要自己算一个数就决定。**

**状态**：✅ 用户已确认 `Clear` 的效果「还不错」。模糊强度不可调一事维持现状。

### ISSUE-016 · CHANGELOG 曾被脚本误截断（已重建）—— 教训：文档没有备份
| 项 | 内容 |
|---|---|
| 发现于 | P07 收尾时重排 CHANGELOG 章节顺序 |
| 严重度 | 高（**资料丢失**） |
| 经过 | 用 PowerShell 按标题切分重排时，`Where-Object { $x -like "*## [P00*" }` 里的**方括号在 `-like` 中是通配符字符类**，导致匹配全部失败；脚本随后把只含第一段的 `$sorted` 写回了源文件，**P01–P07 全部丢失** |
| 损失范围 | CHANGELOG 的 P01–P07 段（P00 完好）。**其它文档均未受影响** |
| 无法恢复 | 工程**没有 git 仓库、没有备份**，原文无法逐字找回 |
| 处置 | 依据 `ROADMAP.md`（含各阶段决策与缺陷表）、`TEST_REPORT.md`、`KNOWN_ISSUES.md`、`docs/*` **重建**，并在重建段落中**如实标注"重建"** |
| 状态 | ⚠️ **已重建，但细节密度低于原文** |

**教训（两条，都很硬）**

1. **不要用 `-like` 匹配含方括号的字面量。** PowerShell 的 `-like` 把 `[` `]` 当通配符字符类。
   应使用 `-eq` / `-match`（配 `[regex]::Escape`）或 `String.Contains`。
2. **改写文件前先备份。** 当时若先 `Copy-Item $p "$p.bak"`，损失是零。
   **这是本会话最该记住的一条**：用脚本改写**内容较多、且无法从别处再生**的文件时，
   必须先落一份副本，无论脚本看起来多简单。

### ISSUE-014 · 启动自检写了却没有任何调用点（已修复）

### ISSUE-013 · `org.json` 在单元测试中是空壳 stub，导致红线逻辑无法离线验证
| 项 | 内容 |
|---|---|
| 发现于 | P03 首次运行单元测试（**29 / 40 失败**） |
| 严重度 | 中高（**影响可测试性**） |
| 现象 | `org.json` 属 Android 框架，在 JVM 单元测试中只有方法签名，一调用即抛 `RuntimeException: Method ... not mocked`。因此所有涉及 JSON 的逻辑（解析正确性、错误映射、"0 不是价格"等**红线**）都无法在无设备环境下验证 |
| 备选方案 | 给测试加第三方 `org.json` 依赖 —— ❌ **否决**：会造成"测过的实现与运行时用的实现是两套代码"，测试结论不可迁移 |
| 处置 | ✅ 自写极小 JSON 解析器 `core/json/Json.kt`（对象/数组/字符串含转义与 `\uXXXX`/数字/布尔/null；解析失败返回 null 不抛异常）。**测试与运行时共用同一份代码** |
| 附带收益 | 提供语义化读取：`positiveLong()` 把 **0 / 负数 / 缺失一律视为「无数据」**，把红线编码进 API 形状 |
| 状态 | ✅ **已解决**（59 个用例全部通过） |

**教训**：**"能不能测"本身就是设计要求**。把数据解析绑在 Android 框架上，
会让最关键的那部分逻辑在无设备环境下变成黑盒 —— 而那些逻辑恰恰是红线所在。
