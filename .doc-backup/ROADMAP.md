### 🟢 P01 实测结论：两条路线**都已跑通核心栈**

**完整矩阵见 `docs/risks.md` §2 与 `TEST_REPORT.md` T-P01-01。**

| 能力 | Kotlin 2.2.10 | Kotlin 2.4.21（**已选定**） |
|---|---|---|
| Compose + 自研导航 | ✅ 11.76 MB | ✅ 11.85 MB |
| 官方 `navigation-compose` | ✅ 11.65 MB | ✅ 11.72 MB |
| 零依赖平台 `Modifier.blur` | ✅ 11.76 MB | ✅ 11.85 MB |

| `haze 1.7.3`（纯模糊） | ✅ 11.73 MB | ✅ 11.78 MB |
| **`haze 2.0.1` + `haze-glass`（折射）** | ❌ metadata 不兼容 | ✅ **12.14 MB** |

> **选定 Kotlin 2.4.21 的唯一收益**：解锁折射式液态玻璃（`haze-glass`）。
> 其余能力两条路线**实测完全一致**，故本次升级**不引入回归风险**。

### ★ 关键验收：新增工具不改公共代码 —— 已实测通过

设计稿要求「新增一个测试工具，**不改首页代码**，即出现在工具列表中」。

- 点击可打开，页面正确渲染（4 件有成交数据物品，区间统计正确排除无成交物品）
- **零崩溃**

### ★ 本轮补上的架构缺口（重要）

实测前发现：`architecture.md` §4.4 承诺的扩展机制**在代码里并不存在** ——
原实现只有「注册表 + 硬编码 `when` 分支」，每加一个工具都得改 `MainActivity`。
**文档承诺高于代码实际能力**，这是必须修掉的差距。

本轮补齐：

| 新增 | 作用 |
|---|---|
| `domain/tool/ToolProvider.kt` | 工具 = 描述 + **页面** + 路由，三合一注册 |
| `domain/tool/ToolNavActions` | 宿主注入的**窄接口**导航能力，工具不依赖根导航器 |
| `domain/tool/AppContainer.kt` | 唯一装配点；新增游戏在此加一项 |
| `GameModule` 契约 | 公共层不依赖具体游戏，接第二款游戏时三角洲 0 改动 |
| `UbToolRegistry.providerByRoute()` | 根导航按路由分发，`when` 里不再有具体工具 |
| `UbToolRegistry.verifyIntegrity()` | 启动自检：id 唯一、路由唯一非空、gameId 已注册 |
| `game/deltaforce/DeltaForceRoutes.kt` | **路由下移到模块层**（详见下方说明） |

### 实测中发现的关键设计点：路由不能放公共层

若把工具路由都写进 `core/navigation/UbRoutes.kt`，每加一个工具就要改一次**共享文件**，
「不改公共代码」当场不成立。故约定：
**应用级路由**留公共层，**工具路由**归游戏模块所有。

## 全局规则（贯穿所有阶段）

> 设计稿第五节：**DeepSeek 每次修改前先检查现有项目，修改后提供可核验的结果，禁止仅凭代码生成成功就宣布功能完成。**

1. 每次开始工作前，先确认当前阶段、当前目标和现有项目状态。
2. 有已有工程时，必须先检查项目结构、关键源文件、Gradle 配置和当前构建状态。
3. 修改代码优先小范围修改，不随意覆盖已有工程。
4. 涉及复杂 UI 时，先分析参考截图，再确定布局与组件方案。
5. 涉及运行异常时，优先分析日志、代码和复现步骤，**不得仅凭截图猜测**。
6. 涉及第三方依赖时，检查版本、许可证、兼容性和维护状态。
7. 涉及数据源时，必须区分 `已验证` / `待验证` / `受限` / `不可用`。
8. 不生成与当前阶段无关的大量代码。
9. **不用空按钮冒充已完成的交互。**
10. **不把编译成功等同于全部业务功能已经完成。**
